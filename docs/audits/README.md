# Saku learning-experience audits

Ten companion audits, all recurring, not one-offs. This is the index — for deciding which audits to run and dispatching them. It is NOT meant to be read by an individual audit's own agent (that agent reads `how-to-run-an-audit.md` plus its own numbered file only — see below for why).

- **01 — naive-learner audit** (`01-naive-learner.md`). A deliberately-ignorant persona walks the app to find *gaps and ordering bugs*: content quizzed before it was taught, confusing UX, dead ends. Doesn't care whether the content itself is correct — only whether it was taught before it was tested, and whether teaching landed.
- **02 — fact-checking audit** (`02-fact-checking.md`). An expert persona reviews the app's actual content to find *correctness and pedagogy bugs*: wrong readings, wrong grammar explanations, unnatural example sentences, wrong pitch accent, or content that's technically correct but poorly explained. Doesn't simulate a learner's progression at all — reviews content directly.
- **03 — UX audit** (`03-ux.md`). A design/QA persona reviews the interface itself — layout, visual consistency, interaction bugs, responsiveness, accessibility — independent of whether the content flowing through it is correct or well-ordered.
- **04 — reachability/coverage audit** (`04-reachability-coverage.md`). Not a walkthrough at all — an algorithmic check of whether everything in the underlying data actually has a path through the real scheduler. Catches the class of bug a sampled walkthrough structurally can't: something that's never reachable at all.
- **05 — data-integrity/ingest audit** (`05-data-integrity-ingest.md`). Checks the generated data pipeline itself (vocab.json, pitch.json, the grammar corpus, etc.) for internal consistency and staleness against its sources — separate from 02, which checks whether specific taught content is correct.
- **06 — content style/voice audit** (`06-content-style-voice.md`). Terminology, tone, and house-style consistency across all user-facing copy — separate from 03, which is layout/visual, not wording.
- **07 — code/architecture audit** (`07-code-architecture.md`). Not learner-facing at all: data/component/API layer consistency, soundness, and scalability of the codebase itself.
- **08 — sync/multi-device audit** (`08-sync-multi-device.md`). Does signing in and using the app across more than one device/browser actually keep progress consistent — no silent data loss, no unresolved conflicts?
- **09 — performance audit** (`09-performance.md`). Real load-time and interaction-latency measurement, especially true COLD-START conditions — with independent re-verification, so a finding isn't just one environment's (or one person's) impression.
- **10 — multi-signal disagreement resolution audit** (`10-multi-signal-disagreement.md`). A smaller, focused audit with two related jobs, both surfaced by the SAK-215/216/218 pronunciation work: (1) whenever a check produces more than one independent signal about the same fact, EVERY disagreement gets triaged and either resolved or explicitly flagged as unresolved; (2) whenever a seed/cache script claims to cover "everything," that claim gets checked against what the live app can actually request.

They're complementary on purpose, each catching a bug class the others structurally can't: a naive learner can't tell you a grammar rule is wrong (they don't know enough to doubt it); an expert reviewer walking through in order doesn't reliably surface "this was quizzed before it was taught"; a walkthrough of any depth can't surface something that's *never reachable at all* (04's whole job); content can be correct (02) while its underlying data pipeline is quietly drifting (05); copy can be individually fine while inconsistent app-wide (06); the product can be flawless while the code underneath it is fragile in ways that will bite the NEXT change (07); everything above can be perfect on ONE device and still lose data the moment a second device enters the picture (08); everything can be correct, well-ordered, well-coded, and consistent while still being slow to actually use (09); and a multi-signal check can quietly under-report by only acting on the disagreements that fit a clean pattern, silently leaving the rest uninvestigated (10 — the exact gap Sam caught in the SAK-215/218 work: 885 of 893 raw disagreements were never actually resolved, just excluded from the confirmed-bug list). Run them separately.

No prior instance of any of these audits was found in Linear or session memory as of 2026-08-28 — if Sam has notes from an earlier run that predate this doc, fold them in and update this folder. Sam's own read on this (2026-08-28): "we've done many many audits like this before and it's clearly not caught them before because i'm still finding bugs every day" — which is exactly why 02 exists as a formal, systematic pass now rather than relying on catching things by ear/eye during ordinary use, and why the verify stage in `how-to-run-an-audit.md` is the DEFAULT, not an optional upgrade.

## To actually run a set of audits

Tell the session that's going to run them to read **`orchestrator.md`** — that's the entry point, and the only file a kickoff prompt needs to point at directly. It covers dispatching each audit (which two files each audit agent reads), capping concurrency, watching for completion, synthesizing every audit's report into one recommendation list, getting Sam's approval, and filing the resulting Linear tickets.

## Structure of this folder, and why

- `orchestrator.md` — the entry point for running a set of audits: dispatch, concurrency, watching, cross-audit synthesis, approval, ticket filing. Read by whatever session is orchestrating a run, not by an individual audit agent.
- `how-to-run-an-audit.md` — the general mechanics for running ONE audit: ground rules, within-audit dispatch shape, find→verify→synthesize, what a report should contain, live-app-access notes. Applies identically to all ten audits. Every individual audit agent reads this.
- `01-naive-learner.md` through `10-multi-signal-disagreement.md` — one file per audit, containing ONLY that audit's own subject, role, and specifics. Nothing in one audit's file depends on reading another's.

**Why physically separate files, not sections in one doc:** an earlier draft was one file with all ten audits as sections, using phrases like "same shape as Audit 1" to avoid repeating shared mechanics. Sam caught the risk: if an audit ever runs on its own (which is the normal case — audits are dispatched independently), a cross-reference to another audit's section is a dangling pointer unless that whole file is in context anyway, which defeats the point of keeping each audit's own briefing small. Separate files make this structurally impossible instead of a discipline to maintain — an individual audit agent is told to read exactly two files (`how-to-run-an-audit.md` + its own numbered file), and there is no third file in reach to accidentally leak from. The orchestrator layer exists for the same reason, one level up: cross-audit concerns (concurrency, sequencing, combining reports) live in `orchestrator.md` alone, not scattered across the ten audit files where they'd have to be repeated or cross-referenced.
